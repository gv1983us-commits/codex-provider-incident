## Technical state

**Incident remains OPEN.** The recent behavior is better than the severe 16–17 September period, but there is still no demonstrated root-cause fix or sustained provider-side resolution.

### 18–20 September: provider failures persist, Hermes survivability improves

The important new distinction is between:

1. **provider-side failure rate**, and
2. **whether a transient provider failure kills the whole Hermes user turn/session**.

After the Hermes update and a full machine reboot, Hermes is materially better at surviving transient Codex failures. Provider retries now often recover inside the same turn instead of turning every burst into a dead session.

That is a Hermes robustness improvement. It does **not** mean the provider symptom disappeared.

### Low-concurrency control

The owner deliberately reduced workload to **one user session / one user work stream**.

The provider failures continued.

On 19 September, the audited logs contain **58 provider-failure attempts**. The deepest observed chain reached **attempt 4/5** with repeated:

`Our servers are currently overloaded. Please try again later.`

The next attempt recovered, so there was **no new terminal 5/5 exhaustion** in that 19 September set.

This is important negative evidence against a simple explanation in which high user-side parallelism is the necessary cause. Reducing to one user work stream did not eliminate the provider failures.

### First substantially usable day

19 September was the first unusual day in this incident period in which the owner could work from morning into the evening with useful continuity, initially in one user stream.

In the evening the owner started a second user stream. On the morning of 20 September two user streams were again active.

So far, the new two-stream interval has not immediately reproduced a terminal 5/5 chain. The current logs show successful calls continuing across both user sessions and internal/subagent activity.

This also means the relationship between concurrency and failure is not a simple linear one: one-stream periods can still contain overloads, while multi-stream periods can sometimes run cleanly.

### Why the incident is still open

The recent improvement changes severity, not status.

- Provider-side `overloaded`, request-processing and transport failures have continued after the Hermes update and clean reboot.
- A 19 September burst still reached **4/5**, one failure short of a terminal retry exhaustion.
- The fact that Hermes now survives many bursts better is valuable containment, but it is not evidence that the OpenAI/Codex serving/admission problem is fixed.
- Recent clean hours cannot retroactively explain or close the repeated 5/5 exhaustions, request IDs, account-scoped/cross-model reports, and Direct ChatGPT/Codex symptoms already documented.
