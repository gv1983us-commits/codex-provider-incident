# MSI: повторные HTML 403 при работающем Lenovo, 4 ноября 2026

Дополнение к [инциденту #6](https://github.com/gv1983us-commits/codex-provider-incident/issues/6). [Публичные агрегаты и якоря](https://github.com/gv1983us-commits/codex-provider-incident/blob/main/evidence/msi-codex-403-20261104.json).

## Установленный результат

По сообщению владельца, **Lenovo продолжает работать, а MSI получает ошибки на той же подписке и в той же домашней сети**. В последующем уточнении 4 ноября владелец сообщил версии: **Lenovo — «22.7», MSI до обновления — «22.2»; обновление MSI выполняется**. Результат работы после обновления ещё не получен. Свежий приложенный журнал относится к MSI; одновременная успешная работа Lenovo в этом файле не измеряется отдельно.

За **4 ноября** журнал содержит **12 явных записей о неудавшейся API-попытке**:

- **9 HTTP 403** с HTML-страницей `Unable to load site` и девятью различными Ray ID;
- **2 TimeoutError** после watchdog-порога **1 200 секунд**;
- **1 сообщение сервиса о перегрузке**.

В этих записях нет `usage_limit_reached` или quota HTTP 429. Поэтому свежий отказ нельзя объяснять прежним октябрьским исчерпанием недельного лимита на основании этого журнала.

Логовая цепочка HTML 403 → предупреждение о credential refresh совпадает с опубликованным [Hermes #141080](https://github.com/NousResearch/hermes-agent/issues/141080). Текущий проверенный upstream-код допускает ошибочное отнесение такого HTML к auth. Это объясняет возможную неправильную обработку ответа клиентом; **причина первоначального HTTP 403 и различия Lenovo/MSI остаётся не установлена**.

Покрытие файла: **20 октября 12:04:18.197 — 4 ноября 15:26:14.379**. Время ниже воспроизводится как записано в файле: часовой пояс в метках не указан. Ранее сбор велся в UTC+3, но свежий файл сам по себе не подтверждает неизменность настройки часов.

Попыткой считается одна timestamped-запись `agent.conversation_loop: API call failed (attempt …)`. Многострочный HTML, сообщения о refresh, retry notices и финальные сводки исчерпания повторов не прибавляются как дополнительные попытки. Внутренних сетевых запросов могло быть больше этих внешних записей.

**Два timeout относятся к одной паре session/thread-маркеров. У последующего 403 в 12:30 другие session и thread.** Их нельзя изображать одной доказанной цепочкой «два timeout → 403», считать одним ходом или назначать общий механизм только по соседству во времени.

Во всех девяти свежих 403 последовательность одинакова:

1. `Credential auth failure persists after 2 refreshes … treating as unrecoverable and allowing fallback to activate`.
2. `PermissionDeniedError`, `HTTP 403 — HTML error page`, **attempt 1/3, not retryable**.
3. Терминальная HTML-страница с `Unable to load site` и Ray ID.

Последний Ray ID: **`a55349ddbbdef6db`**, время **14:30:47**. Все девять сохранены в публичных агрегатах для технической корреляции. IP, session/thread IDs и идентификатор credential pool исключены.

Текст про два refresh — сообщение локального recovery-механизма, не точная выписка двух OAuth HTTP-запросов. Разрешение fallback не доказывает, что резервный провайдер действительно включился и выполнил запрос. Все девять outer failures помечены nonretryable; это не девять обычных автоматических повторов одной операции.

Значит, симптом не возник впервые 4 ноября; свежие данные подтверждают его повторение и форму ответа, ранее не установленную по сокращённой сводке.

В старой части файла присутствуют quota 429. Их нельзя переносить на 3–4 ноября: в свежих окнах таких отказов нет. Отдельные `Payment Required` от `web_extract`/Firecrawl также относятся к другому инструментальному маршруту и не являются доказательством исчерпания Codex-подписки.

## Почему сообщение об авторизации может вводить в заблуждение

Проверен upstream Hermes на commit **`71736c9f32597bbca9d89cede5aa136e55946b2f`**, актуальном при исследовании 4 ноября. Это **не подтверждение commit, фактически запущенного на MSI**. После первоначального разбора владелец уточнил номер версии до обновления — «22.2», а на Lenovo — «22.7». Точная сборка, локальные изменения и загрузка нового кода уже работающим процессом пока не проверены; номер версии со слов владельца не заменяет такую проверку.

В [agent/error_classifier.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/error_classifier.py#L1075-L1088) обработчик 403 сначала проверяет transient/billing и известные признаки страницы блокировки. Если они не совпали, выбирается auth fallback. В списке признаков, строки 453–461, отсутствуют **`unable to load site`** и **`cloudflare ray id`**.

В [agent_runtime_helpers.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/agent_runtime_helpers.py#L1083-L1093) auth-классификация запускает восстановление учётных данных. В [credential_auth_recovery.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/credential_auth_recovery.py#L131-L165) refresh вызывается до сравнения счётчика с лимитом; поэтому фраза «after 2 refreshes» не является точным счётчиком запросов на проводе.

Таким образом, **само предупреждение о credential auth failure не доказывает истечение, отзыв или неправильность токена**. Оно может быть следствием классификации HTML-страницы. По форме ответа вероятен отказ веб/edge-слоя на пути к API; конкретный уровень, правило и причина требуют дальнейшего подтверждения.

Автор описывает Windows, успешный OAuth, тот же `openai-codex` endpoint, HTML `Unable to load site`, Ray ID и предупреждение после refresh. Это близкое совпадение сигнатуры; у него не было нашего сравнения двух устройств.

В [комментарии от 18 октября](https://github.com/NousResearch/hermes-agent/issues/141080#issuecomment-6249887805) предложен патч двух недостающих маркеров. Проверенный текущий upstream их не содержит. Заявленную fork-ветку сейчас прочитать не удалось, подтверждённого upstream merge не найдено. Поэтому обещать исправление обычным обновлением оснований нет. **Исправление классификации уберёт неправильную обработку auth, но само по себе не устранит исходный HTTP 403.**

После уточнения версий отдельно сопоставлены официальные теги: **v0.22.2 — `d923a5eb487a17c0a68801bba9ef0f56c81040a8`**, **v0.22.7 — `b200f5bc60e31588ba2cb60e288029c4a54ba5fa`**. Список `_UPSTREAM_BLOCKED_PATTERNS` и функция `_status_403()` в них одинаковы: оба нужных маркера отсутствуют, завершающий auth fallback сохранён. Первичные исходники: [v0.22.2, строки 1028–1041](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/agent/error_classifier.py#L1028-L1041) и [v0.22.7, строки 1075–1088](https://github.com/NousResearch/hermes-agent/blob/b200f5bc60e31588ba2cb60e288029c4a54ba5fa/agent/error_classifier.py#L1075-L1088); списки маркеров соответственно в строках 440–444 и 457–461. **Обновление до 0.22.7 не содержит именно этого исправления классификатора.** Это не доказывает, что другие изменения версии не могут повлиять на наблюдаемый результат; итог обычной работы MSI после обновления ещё неизвестен.

В [OpenAI/Codex #57039](https://github.com/openai/codex/issues/57039#issuecomment-6630371149) есть независимое сообщение **4 ноября** о Windows HTTP 403/`cloudflare_challenge` на account/settings/realtime и dictation. Это другой клиент и другие маршруты: современный пример класса отказов, не установленная общая причина с данным Hermes-эпизодом.

При проверке 4 ноября [OpenAI Status](https://status.openai.com/) сообщает об отсутствии известной общей аварии; [история](https://status.openai.com/history) не содержит отдельного ноябрьского инцидента этого Codex 403. Агрегированный статус не опровергает отказ конкретного клиента, о чём страница статуса сама делает оговорку.

## Уточнение владельца: расход лимита и работа двух сессий

Источник этого раздела — последующее сообщение владельца **4 ноября 2026 года**. Это наблюдения за рабочими сессиями и индикатором лимита, отдельно от подсчёта ошибок в приложенном файле. Выгрузки серверного учёта расхода и точных времён сброса пока нет.

| Период, по сообщению владельца | Наблюдение | Что можно зафиксировать |
|---|---|---|
| Первый из двух последовательных эпизодов примерно неделю назад | Включённый лимит Pro исчерпан примерно за двое суток; затем произошёл сброс лимита, отнесённый владельцем к провайдеру | Длительность приблизительная; точные границы периода и механизм сброса не установлены |
| Второй последовательный эпизод | Снова около двух суток до исчерпания, затем ещё один сброс лимита | Это второй эпизод расхода в описанной последовательности, а не утверждение о покупке ещё одной подписки |
| Текущее состояние | Около 20% лимита в сутки | Оценка владельца по текущему наблюдению; не фиксированный норматив тарифа |

Владелец подчёркивает, что **объём работ всё время постоянен: две работающие Hermes-сессии**. При трёх открытых сессиях **одна или две простаивают в ожидании**. Поэтому число открытых сессий нельзя считать числом одновременно производящих результат работников; линейного роста полезной работы при добавлении третьей сессии владелец не наблюдает.

Если каждый ранний эпизод начинался с полного доступного лимита, исчерпание за двое суток соответствует в среднем **около 50 процентных пунктов индикатора в сутки**. Текущие примерно 20 пунктов в сутки означают **примерно в 2,5 раза меньшую скорость расхода**. При сохранении этой скорости полный лимит соответствовал бы примерно **пяти суткам** работы. Это условный пересчёт наблюдаемых процентов, а не прогноз срока следующего сброса или гарантия ёмкости подписки.

Следствие для инцидента: прежние два дня нельзя подавать как устойчивую ёмкость Pro при этой рабочей нагрузке. Зафиксировано изменение расхода, которое требует объяснения при сопоставлении периодов. При этом постоянный объём задач и число активных сессий сами по себе ещё не устанавливают равенство токенов, размера контекста, cache hit, повторов и фактического серверного учёта между периодами. Из этих наблюдений нельзя отдельно вывести изменение тарифных коэффициентов, ручной сброс, ошибочное начисление или конкретный лимит параллелизма на стороне провайдера.

Сбросы сохраняем как **два наблюдения владельца о восстановлении лимита**, без назначения точных дат и без утверждения, что это были штатные недельные сбросы или подтверждённые ручные действия поддержки. Улучшение расхода уже сообщено во время обновления MSI; приписывать его результату ещё не завершённого обновления нельзя. HTML 403, учёт лимита и ожидание при трёх сессиях остаются отдельными наблюдениями до установления причинной связи.

## Что означает сравнение Lenovo и MSI

Наблюдение владельца важно: другая машина с той же подпиской остаётся работоспособной. Оно не поддерживает простое объяснение «весь аккаунт недоступен» и требует сравнения конкретных клиентов.

Версии клиента действительно различались по сообщению владельца: Lenovo «22.7», MSI «22.2». Обновление MSI позволяет убрать это известное различие; результат после обновления ожидается. Одна домашняя сеть ещё не подтверждает одинаковый фактический маршрут двух процессов. Также могут различаться локальный proxy/VPN, IPv4/IPv6, клиентский транспорт, авторизационная сессия, модель и размер контекста. В этом разборе ни один из этих вариантов не назначен доказанной причиной; бан аккаунта/IP, география и потеря подписки не установлены.

Для следующего шага достаточно чтения локальных данных MSI: фактический executable работающего процесса, HEAD/dirty-status его checkout, наличие маркеров в classifier. Затем можно сопоставить это с работающим Lenovo. Новые запросы к модели и переустановка для такого сбора не нужны.

### Минимальная проверка установленного кода MSI

Путь взят из приложенного лога. Команды читают установленный код и git-метаданные; Hermes не запускается, секреты и auth-файлы не читаются. Проверка checkout ещё не доказывает, что каждый уже запущенный процесс загрузил именно эти файлы.

```powershell
$hermesSource = Join-Path $env:LOCALAPPDATA 'hermes\hermes-agent'
$classifier = Join-Path $hermesSource 'agent\error_classifier.py'
if (Test-Path -LiteralPath $classifier) {
    [pscustomobject]@{
        Source = $hermesSource
        HasHtml403Marker = [bool](Select-String -LiteralPath $classifier -Pattern 'unable to load site' -SimpleMatch -Quiet)
    } | Format-List
    if (Get-Command git -ErrorAction SilentlyContinue) {
        git -C $hermesSource rev-parse HEAD
        git --no-optional-locks -C $hermesSource status --short -- agent/error_classifier.py agent/credential_auth_recovery.py agent/agent_runtime_helpers.py
    }
} else {
    "Hermes source not found: $hermesSource"
}
```

Исходный лог не изменялся. Публичное дополнение содержит только необходимые технические признаки и корреляционные Ray ID; полные HTML, IP, авторизация, частные задачи и локальные идентификаторы не публикуются.
