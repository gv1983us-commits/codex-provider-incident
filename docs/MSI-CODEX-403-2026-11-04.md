# MSI: повторные HTML 403 при работающем Lenovo, 4 ноября 2026

Дополнение к [инциденту #6](https://github.com/gv1983us-commits/codex-provider-incident/issues/6). [Публичные агрегаты и якоря](https://github.com/gv1983us-commits/codex-provider-incident/blob/main/evidence/msi-codex-403-20261104.json).

## Установленный результат

По сообщению владельца, **Lenovo продолжает работать, а MSI получает ошибки на той же подписке и в той же домашней сети**. Свежий приложенный журнал относится к MSI; одновременная успешная работа Lenovo в этом файле не измеряется отдельно.

За **4 ноября** журнал содержит **12 явных записей о неудавшейся API-попытке**:

- **9 HTTP 403** с HTML-страницей `Unable to load site` и девятью различными Ray ID;
- **2 TimeoutError** после watchdog-порога **1 200 секунд**;
- **1 сообщение сервиса о перегрузке**.

В этих записях нет `usage_limit_reached` или quota HTTP 429. Поэтому свежий отказ нельзя объяснять прежним октябрьским исчерпанием недельного лимита на основании этого журнала.

Логовая цепочка HTML 403 → предупреждение о credential refresh совпадает с опубликованным [Hermes #141080](https://github.com/NousResearch/hermes-agent/issues/141080). Текущий проверенный upstream-код допускает ошибочное отнесение такого HTML к auth. Это объясняет возможную неправильную обработку ответа клиентом; **причина первоначального HTTP 403 и различия Lenovo/MSI остаётся не установлена**.

## Источник и способ подсчёта

Источник: `errors(2).log`, **1 560 572 байта**, **8 820 физических строк**, **3 890 записей с меткой времени**. SHA-256: `1a3f2043567d78595835d378a30234c29181f26e1e05463da677c8b66ec64ada`.

Покрытие файла: **20 октября 12:04:18.197 — 4 ноября 15:26:14.379**. Время ниже воспроизводится как записано в файле: часовой пояс в метках не указан. Ранее сбор велся в UTC+3, но свежий файл сам по себе не подтверждает неизменность настройки часов.

Попыткой считается одна timestamped-запись `agent.conversation_loop: API call failed (attempt …)`. Многострочный HTML, сообщения о refresh, retry notices и финальные сводки исчерпания повторов не прибавляются как дополнительные попытки. Внутренних сетевых запросов могло быть больше этих внешних записей.

Оба watchdog-эпизода показывают `context=~853,350 tokens`, тело запроса **2 132 899 байт**, `stream_opened=true`, завершение через ReadError после остановки соединения. Это большой рабочий контекст и два длительных ожидания, но в этих записях нет подтверждённой ошибки превышения контекстного лимита.

**Два timeout относятся к одной паре session/thread-маркеров. У последующего 403 в 12:30 другие session и thread.** Их нельзя изображать одной доказанной цепочкой «два timeout → 403», считать одним ходом или назначать общий механизм только по соседству во времени.

Во всех девяти свежих 403 последовательность одинакова:

1. `Credential auth failure persists after 2 refreshes … treating as unrecoverable and allowing fallback to activate`.
2. `PermissionDeniedError`, `HTTP 403 — HTML error page`, **attempt 1/3, not retryable**.
3. Терминальная HTML-страница с `Unable to load site` и Ray ID.

Последний Ray ID: **`a55349ddbbdef6db`**, время **14:30:47**. Все девять сохранены в публичных агрегатах для технической корреляции. IP, session/thread IDs и идентификатор credential pool исключены.

Текст про два refresh — сообщение локального recovery-механизма, не точная выписка двух OAuth HTTP-запросов. Разрешение fallback не доказывает, что резервный провайдер действительно включился и выполнил запрос. Все девять outer failures помечены nonretryable; это не девять обычных автоматических повторов одной операции.

## Предыдущий день и историческое совпадение

3 ноября зарегистрированы **63 APITimeoutError с 04:21:03 до 06:35:38**, а также **15 сообщений provider auto-recovery** и три терминальных сводки после исчерпания повторов. В соответствующих runtime-строках видны ConnectTimeout до открытия потока. Эта серия отличается от последующих HTML-отказов.

Первый такой HTML 403 в данном файле встречается уже **21 октября 08:24:53.156** (строка 364; HTML — 365–417). Весь файл содержит 24 явных HTML 403 и 24 Ray ID. Значит, симптом не возник впервые 4 ноября; свежие данные подтверждают его повторение и форму ответа, ранее не установленную по сокращённой сводке.

В старой части файла присутствуют quota 429. Их нельзя переносить на 3–4 ноября: в свежих окнах таких отказов нет. Отдельные `Payment Required` от `web_extract`/Firecrawl также относятся к другому инструментальному маршруту и не являются доказательством исчерпания Codex-подписки.

## Почему сообщение об авторизации может вводить в заблуждение

Проверен upstream Hermes на commit **`71736c9f32597bbca9d89cede5aa136e55946b2f`**, актуальном при исследовании 4 ноября. Это **не подтверждение версии, фактически запущенной на MSI**: октябрьскую ревизию `d923a5e…` не объявляем текущей.

В [agent/error_classifier.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/error_classifier.py#L1075-L1088) обработчик 403 сначала проверяет transient/billing и известные признаки страницы блокировки. Если они не совпали, выбирается auth fallback. В списке признаков, строки 453–461, отсутствуют **`unable to load site`** и **`cloudflare ray id`**.

В [agent_runtime_helpers.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/agent_runtime_helpers.py#L1083-L1093) auth-классификация запускает восстановление учётных данных. В [credential_auth_recovery.py](https://github.com/NousResearch/hermes-agent/blob/71736c9f32597bbca9d89cede5aa136e55946b2f/agent/credential_auth_recovery.py#L131-L165) refresh вызывается до сравнения счётчика с лимитом; поэтому фраза «after 2 refreshes» не является точным счётчиком запросов на проводе.

Таким образом, **само предупреждение о credential auth failure не доказывает истечение, отзыв или неправильность токена**. Оно может быть следствием классификации HTML-страницы. По форме ответа вероятен отказ веб/edge-слоя на пути к API; конкретный уровень, правило и причина требуют дальнейшего подтверждения.

## Что означает сравнение Lenovo и MSI

Наблюдение владельца важно: другая машина с той же подпиской остаётся работоспособной. Оно не поддерживает простое объяснение «весь аккаунт недоступен» и требует сравнения конкретных клиентов.

Одна домашняя сеть ещё не подтверждает одинаковый фактический маршрут двух процессов. Могут различаться локальный proxy/VPN, IPv4/IPv6, клиентский транспорт, версия Hermes, авторизационная сессия, модель и размер контекста. В этом разборе ни один из этих вариантов не назначен доказанной причиной; бан аккаунта/IP, география и потеря подписки не установлены.

Для следующего шага достаточно чтения локальных данных MSI: фактический executable работающего процесса, HEAD/dirty-status его checkout, наличие маркеров в classifier. Затем можно сопоставить это с работающим Lenovo. Новые запросы к модели и переустановка для такого сбора не нужны.

### Минимальная проверка установленного кода MSI

Путь взят из приложенного лога. Команды читают установленный код и git-метаданные; Hermes не запускается, секреты и auth-файлы не читаются. Проверка checkout ещё не доказывает, что каждый уже запущенный процесс загрузил именно эти файлы.

```powershell
$hermesSource = Join-Path $env:LOCALAPPDATA 'hermes\hermes-agent'
$classifier = Join-Path $hermesSource 'agent\error_classifier.py'
if (Test-Path -LiteralPath $classifier) {
    [pscustomobject]@{
        Source = $hermesSource
        HasHtml403Marker = [bool](Select-String -LiteralPath $classifier -Pattern 'unable to load site' -SimpleMatch -Quiet)
    } | Format-List
    if (Get-Command git -ErrorAction SilentlyContinue) {
        git -C $hermesSource rev-parse HEAD
        git --no-optional-locks -C $hermesSource status --short -- agent/error_classifier.py agent/credential_auth_recovery.py agent/agent_runtime_helpers.py
    }
} else {
    "Hermes source not found: $hermesSource"
}
```

Исходный лог не изменялся. Публичное дополнение содержит только необходимые технические признаки и корреляционные Ray ID; полные HTML, IP, авторизация, частные задачи и локальные идентификаторы не публикуются.
