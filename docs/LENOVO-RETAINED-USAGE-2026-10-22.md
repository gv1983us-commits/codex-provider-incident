# Lenovo: сохранённая статистика использования, 8 сентября — 22 октября 2026

Дополнение к [инциденту #6](https://github.com/gv1983us-commits/codex-provider-incident/issues/6) и [основному отчёту](https://github.com/gv1983us-commits/codex-provider-incident/blob/main/docs/CODEX-WEEKLY-ALLOWANCE-2026-10-22.md). Все локальные даты ниже — **Europe/Istanbul, UTC+03:00**. [Публичные агрегаты JSON](https://github.com/gv1983us-commits/codex-provider-incident/blob/main/evidence/lenovo-retained-usage-20261022.json).

## Результат

Владелец выгрузил накопленные счётчики напрямую из локальных баз Lenovo. В полученном архиве есть история **с 8 сентября по 22 октября**. Это существенно расширяет прежние журналы успешных вызовов, сохранённые лишь с 18 октября. Более ранняя история до 8 сентября в этой выгрузке не представлена.

В трёх базах суммарно записаны **119 135 API-вызовов: 115 531 основной и 3 604 вспомогательных**. Это сумма сохранённых локальных счётчиков, не независимо восстановленный список уникальных запросов провайдера. Основная база содержит почти всю нагрузку: **115 503 main + 3 599 auxiliary = 119 102**.

Две основные таблицы согласованы **по каждой сессии**, а не только по общей сумме. Разница между их итогами объясняется отдельным учётом auxiliary. Ошибка арифметического суммирования в этих данных не обнаружена.

**Существенное уточнение прежнего отчёта:** журнал завершённых API-вызовов уже включает часть `background_review`. Сумму всего auxiliary из БД нельзя прибавлять к прежнему completed-call total. Для Sol 6 и Sol 6.1 перекрытие подтверждено точным совпадением вызовов, полного входа, выхода и cache-read.

- Ошибок обхода и чтения в экспортном отчёте нет; все три базы имеют статус `ok`.
- Сессии и строки использования разных моделей экспортированы без фильтра по датам. Отсутствующие ранее удалённые или никогда не записанные данные этим не восстанавливаются.

## 2. Как считать токены

В проверенной upstream-схеме Hermes поле `input_tokens` означает **вход без чтения и записи кеша**. Полный вход вычисляется как:

`full_prompt = input_tokens + cache_read_tokens + cache_write_tokens`.

В строках `agent.log` поле `in=` уже содержит полный вход. Сравнивать его только со столбцом БД `input_tokens` нельзя. Это проверено по [нормализации](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/agent/usage_pricing.py#L626-L678), [передаче счётчиков в БД](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/agent/turn_usage.py#L254-L281) и точному численному совпадению с Lenovo-логами ниже.

| Сохранённый счётчик, все три базы | Main | Auxiliary | Всего |
|---|---:|---:|---:|
| Вход без кеша | 1 114 277 935 | 82 738 569 | **1 197 016 504** |
| Чтение из кеша | 21 641 925 552 | 640 379 904 | **22 282 305 456** |
| Запись в кеш | 0 | 0 | 0 |
| Полный вход | 22 756 203 487 | 723 118 473 | **23 479 321 960** |
| Выход | 63 969 453 | 6 355 260 | **70 324 713** |
| Reasoning, детализация выхода | 24 840 978 | 892 065 | **25 733 043** |

Чтение из кеша составляет **94,90% полного входа** в сохранённом учёте. Это объём повторной обработки контекста, а не 23,48 млрд уникальных пользовательских токенов. Высокая общая доля кеша не доказывает корректность каждого запроса или отсутствие отдельных проблем.

`reasoning_tokens` извлекается из детализации output; в формуле Hermes его не прибавляют к `output_tokens` повторно. `cache_write_tokens=0` описывает сохранённый счётчик, а не доказывает отсутствие любых серверных операций создания кеша.

Из 119 135 вызовов **119 123 явно помечены `openai-codex`**, восемь не имеют provider attribution, четыре относятся к другим маршрутам. Поэтому общую сумму нельзя без оговорки объявлять числом вызовов OpenAI. Публичная JSON-сводка разделяет эти группы и не содержит частных адресов моделей.

## 3. Основной и вспомогательный учёт

Основные изменения счётчиков отражаются и в `sessions`, и в `session_model_usage` с пустым `task`. Auxiliary записывается в модельную таблицу с непустым `task`. Эти правила видны в [writer Hermes](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_state_usage.py#L273-L391).

Для всех **1 188 сессий** проверены шесть полей: calls, input, output, cache read/write и reasoning. Сумма main-строк модели совпала с соответствующей сессией во всех случаях. Две таблицы целиком складывать нельзя.

| Вспомогательная задача, все базы | Вызовы | Вход без кеша | Выход |
|---|---:|---:|---:|
| Background review | 2 667 | 63 548 960 | 1 927 045 |
| Сжатие контекста | 352 | 18 543 500 | 4 240 197 |
| Approval | 304 | 161 313 | 18 906 |
| Vision | 265 | 479 821 | 168 653 |
| Названия сессий | 16 | 4 975 | 459 |
| **Всего** | **3 604** | **82 738 569** | **6 355 260** |

Вспомогательные задачи дают **3,03% учтённых вызовов и 9,04% выхода**. Сжатие контекста — крупнейшая auxiliary-категория по выходным токенам. Эти доли не равны долям списания недельного лимита или credits: нет провайдерского правила пересчёта для данного аккаунта и периода.

Строк `goal_judge` в выгрузке нет. Это отсутствие соответствующей записи, а не доказательство отсутствия выполнения таких задач. Ранее найденные route-selection события сами по себе не подтверждают завершённый платный вызов.

Для моделей, появившихся в пределах сохранённого периода `agent.log`, получено следующее совпадение:

|---|---:|---:|

| **Сумма = completed calls в логах** | **10 173** | **184** |
| **Полный вход, совпал с логами** | **1 955 460 500** | **36 603 350** |
| **Выход, совпал с логами** | **5 198 100** | **57 323** |
| **Cache-read, совпал с явно записанным кешем логов** | **1 865 136 000** | **33 728 384** |

Эти значения проверены как по прежней JSON-сводке, так и независимо по `joint_completed_calls.csv`. В сравниваемых группах `cache_write_tokens=0`.

Следовательно, прежняя log-популяция включает `background_review`; она не тождественна только DB main. Если прибавить к ней весь auxiliary из БД, повторно посчитаются как минимум **247 вызовов и 145 449 выходных токенов** этих двух моделей.

Для GPT-6 Sol БД дополнительно содержит **24 auxiliary-вызова** других типов: 20 compression, три approval и один title generation. Их выход — **201 978 токенов**, вход без кеша — **1 331 016**. Они находятся за пределами точно совпавшей группы main + background review. Для точного имени GPT-6.1 Sol 900k таких дополнительных категорий нет. Это не устанавливает полное покрытие остальных моделей или всех inference-путей.

Механизм согласуется с исходником: [background review создаёт обычный AIAgent, отключая его прямую session DB-запись](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/agent/background_review.py#L957-L997); [обычный usage logger работает независимо от наличия DB](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/agent/turn_usage.py#L181-L281). Затем результаты review записываются в родительский auxiliary-счётчик.

Это совпадение агрегатов, а не построчное соединение по response ID. Оно не превращает отсутствующий cache-field у отдельной строки лога в подтверждённый ноль.

## 6. Почему нельзя точно разделить расход между Pro и Plus

Известная от владельца дата перехода на Plus — **3 или 4 октября**, точное время неизвестно. Это внешнее описание истории аккаунта; DB не содержит тарифного события или account ID.

На каждой из контрольных границ **3, 4 и 5 октября в 00:00** остаются три неоднозначные сессии: две с записанным интервалом через границу и одна без времени окончания. В них накоплено:

- **28 944 основных вызова — 25,06%** main-счётчика основной базы;
- **18 322 771 выходной токен — 28,64%**;
- **7 393 173 120 cache-read токенов — 34,16%**.

Это весь lifetime-счётчик этих сессий, **не расход за 3–4 октября**. Если учитывать любое время активации в течение обоих дней, неопределённость ещё шире: к ней добавляются записи, начатые в эти дни.

Маркер **20 октября 12:04:02.662** — первая сохранённая runtime-запись MSI, не время покупки Pro. В основной Lenovo-базе его пересекают или не имеют известного окончания семь сессий с **27 002 main calls**. По модельным `first_seen`/`last_seen` этот маркер пересекают четыре записи с **9 989 main/aux calls**. Это разные уровни агрегации; их суммы не складываются.

Сами `first_seen`/`last_seen` также не являются журналом каждого запроса. Обычный writer фиксирует время записи накопленного использования; запись может происходить после очереди/flush. [Миграция v20](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/hermes_state_schema.py#L105-L133) переносит исторические суммы с `first_seen=started_at` и `last_seen=COALESCE(ended_at, started_at)`, а не восстанавливает время каждого вызова.

Поэтому таблицы пересечения границ — описание свойств сохранённых агрегатов, не строгая выписка фактических списаний до и после перехода. Дневной график, относящий всю сумму к старту сессии, для этого сравнения неприменим.

## 7. Денежный учёт и предел вывода

Во всех 1 188 session rows `actual_cost_usd` отсутствует (`NULL`). В модельной таблице оно записано нулём; большинство main-строк имеют `cost_status=included`, источник цены — `none`. Это форма локального учёта подписки, **не подтверждение бесплатной работы и не история списаний купленных credits**.

Выгрузка не содержит размера выданного недельного лимита, движения остатка, времени изменения entitlement или привязки каждого вызова к прежней/новой учётке. Поэтому она не доказывает и не опровергает описанный владельцем переход «Plus почти две недели работал по прежнему объёму, затем лимит резко закончился».

Объём использования и его структура теперь подтверждены значительно лучше. Причина резкого изменения доступного объёма и зависаний остаётся отдельным вопросом. Наблюдения о сроке работы первого Pro и нового Pro сохраняются как сведения владельца, а не становятся автоматически коэффициентом изменения квоты.

## 8. Проверки и границы реализации

- Main-счётчики совпадают между таблицами для каждой сессии во всех трёх базах.
- Пересечений session IDs между базами и точных дублей экспортированных строк нет.
- В db_001 все 1 163 parent links разрешаются; отсутствующих родителей и циклов нет. Экспорт не содержит типа связи, поэтому по одному `parent_session_id` нельзя отличить subagent от compaction.
- Не найдено parent/child-пар с одинаковым полным вектором счётчиков или модельных first_seen раньше создания дочерней сессии. Это проверка очевидных повторов, не доказательство уникальности всех физических запросов.
- Нет будущих timestamp относительно экспорта, обратных first/last-интервалов и usage за пределами записанных session-границ.
- Мост DB ↔ completion logs подтверждён по четырём метрикам для двух моделей.

Исходники выше закреплены на **MSI `d923a5e…`**. Lenovo использует **`c7c2595…dirty`**, чьи локальные изменения не проверены. Корректный вывод: выгрузка Lenovo внутренне согласована и соответствует указанной upstream-схеме; фактическая установленная Lenovo-реализация целиком не аттестована.

Публичная сводка содержит только агрегаты, временные границы и контрольные суммы источника. Анонимизированные session IDs, частные адреса моделей, содержимое задач и локальные пути не публикуются.
